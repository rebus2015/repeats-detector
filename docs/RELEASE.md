# Подготовка выпуска

## Поддерживаемый сценарий

В MinIO заранее размещены PCM WAV: 16 кГц, один канал, signed PCM 16 бит.
Сервис получает s3_url через RabbitMQ, читает WAV в RAM, ищет тот же звуковой фрагмент
среди задач того же scope за последние 60 минут, публикует результат через outbox.
Конвертации входных MP3/AAC/Opus и распознавания текста в рабочем пути нет.

Для пилота рекомендуются фрагменты от 5 секунд; устойчивее результаты от 10 секунд.
MIN_MATCH_SECONDS=2 — минимальная подтверждённая длительность, а не обещание находить
любую двухсекундную запись. Стандартный лимит WAV — 128000000 байт, отпечатков — 1000000.
Не все файлы допустимого размера обязательно укладываются в лимит отпечатков.

## Предварительные критерии

Это предложенные критерии локального пилота, не согласованный SLA:

- точные обрезки 5–30 секунд: 100% обнаружений на новом контрольном прогоне;
- обрезки с искусственным шумом 18/8 dB, длина >=10 секунд: recall >=95% на статической галерее;
- для 5-секундных зашумлённых запросов качество приводится отдельно, без гарантии;
- для <=30-секундных задач при 4 outstanding / 2 workers: p95 <=5 секунд, p99 <=10 секунд локально;
- после SIGKILL сервиса/брокера/БД задачи восстанавливаются, состояние остаётся согласованным;
- резервная копия восстанавливается в отдельную БД без нарушения ссылочной целостности;
- precision требует вручную проверенных отрицательных примеров. Разные имена файлов
  не являются доказательством отсутствия общего аудио.

## Конфигурация целевого окружения

1. Подготовить отдельные PostgreSQL, RabbitMQ с quorum queues, MinIO и SigNoz/collector.
2. Выполнить `DATABASE_URL=... go run ./cmd/migrate` с ролью владельца БД.
3. Создать runtime LOGIN средствами платформы; применить grants из
   `deploy/postgres-workload-role.sql`. Пароли не сохранять в SQL/репозитории.
4. Выдать S3 workload только GetObject на используемый prefix; пример —
   `deploy/minio-workload-policy.json`. Загрузка тестового корпуса — отдельная роль.
5. Создать `deploy/production.env` по примеру; реальные значения исключены из Git
   и Docker build context. AWS credentials передаются через Docker secret либо workload role.
6. Настроить доверенные сертификаты: PostgreSQL verify-full, amqps, HTTPS S3/OTLP.
   В контейнере нужен CA целевого окружения; для частного CA смонтировать trust bundle
   и указать SSL_CERT_FILE. Не отключать проверку сертификатов.
7. Использовать `deploy/compose.production.yaml` с reviewed image digest, REQUIRE_TLS=true,
   AUTO_MIGRATE=false. Миграции и runtime роли разделены.
8. Импортировать dashboard, задать alerts и получателей, проверить тестовое оповещение.
9. Повторить корпус, нагрузку, восстановление и резервное копирование уже на целевом сервере.

Локальный MinIO собирается из фиксированного upstream tag в `deploy/Minio.Dockerfile`.
Это тестовая сборка: конкретный эксплуатационный дистрибутив и его обновления выбираются
для целевого окружения. Код сервиса от способа поставки MinIO не зависит.

## Резервное копирование и восстановление

`tools/backup_restore.py` делает custom-format pg_dump и pg_restore во временную БД,
проверяет rd_tasks / rd_prints / rd_outbox и удаляет только временную БД. Он не заменяет
рабочую БД. Существующий архив не перезаписывается. Архивы содержат метаданные задач;
храните их за пределами репозитория, с шифрованием и контролем доступа.

Для эксплуатации нужны расписание, внешнее хранилище и согласованные RPO/RTO.
При RPO меньше интервала полных backup настройте WAL archiving/PITR средствами PostgreSQL.
После восстановления БД возможна повторная доставка event_id: получатель обязан устранять
повторы. MinIO и RabbitMQ требуют собственных политик сохранности и восстановления.

## Обновление и возврат версии

Отпечатки landmark-v2 остаются совместимыми: упаковка хеша не менялась. Изменились
политика retrieval и ограничения ресурсов; перед обновлением сравнить результаты на
своём корпусе. Сначала обновить один экземпляр в пилоте, затем остальные. При смене
самого fingerprint Version нужны отдельная версия индекса и переходное заполнение.

Вернуть предыдущий image можно без отката схемы (текущая схема v1 сохранена).
Не удалять outbox и не менять task_id при обычном повторе доставки. Для исправленного
входа с тем же прежним task_id будет ErrConflict; используйте новый task_id.

В Compose имя узла RabbitMQ должно оставаться неизменным при существующем томе.
Новый стенд использует hostname=rabbitmq. В текущем локальном .env закреплено прежнее
имя узла, чтобы не потерять доступ к уже существующим очередям. Не меняйте его при
повторном создании контейнера. Одноузловой стенд не подтверждает отказоустойчивость кластера.
