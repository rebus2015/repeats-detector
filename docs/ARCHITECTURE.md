# Архитектура первой версии

## Решения

1. Локальные спектральные ориентиры и временные пары — экспериментальный основной метод.
   FFT 1024, hop 256 при 16 кГц; кадр 16 мс. Не более трёх локальных максимумов в окрестности ±3 кадра / ±3 частотных бина,
   до шести временных пар на максимум на расстояниях 4–64 кадра. Частоты квантованы
   по 2 FFT-бина, расстояния по времени — по 2 кадра. Спектры хранятся в кольце из 7 кадров.
   Coarse вариант для эксперимента использует 4 бина и не применяется рабочим сервисом.
2. Кандидаты получаются равенством хешей. Проверка группирует голоса по треку и временному сдвигу
   с допуском ±2 кадра; один кадр запроса учитывается однократно и требует совпадения минимум двух разных хешей. Проверяются длительность,
   покрытие и допустимый разрыв. Пороги по умолчанию: 2 секунды, 12 независимых кадров,
   покрытие 0.08, разрыв не более 0.8 секунды. Это исходные значения для калибровки, не SLO.
3. Индекс — PostgreSQL с составным индексом scope/version/hash/time. Задачи, отпечатки
   и outbox фиксируются атомарно. Отдельное векторное хранилище пока не оправдано измерениями.
4. Поиск и запись сериализованы advisory transaction lock по scope. Уровень READ COMMITTED
   позволяет поиску после ожидания блокировки видеть предыдущий commit. Загрузка и FFT вне транзакции.
   Разные области независимы; одна большая область ограничивает горизонтальное масштабирование.
5. Публикация outbox под FOR UPDATE SKIP LOCKED. Row lock удерживается до publisher confirm;
   нужны достаточные соединения и короткий publish timeout. Publisher переиспользует connection/channel,
   сериализует confirms, ограничивает сокет deadline и пересоздаёт соединение после ошибки.
6. Входная очередь quorum, manual Ack, prefetch равен числу workers. DLQ и выходная очередь durable.
   При временных сбоях пауза и Nack/requeue; постоянные ошибки идут в DLQ. Лимит повторов проверяется по x-acquired-count / x-delivery-count;
   это учитывает изменение семантики Nack в RabbitMQ 4.3.
7. Поиск: точные границы последних 60 минут по часам БД. Очистка запускается каждые 5 минут:
   индекс старше 90 минут удаляется батчами по 50 000; задачи старше 7 дней — по 1000,
   только при отсутствии pending outbox. За один запуск выполняются несколько отдельных батчей
   до очистки или исчерпания 30-секундного бюджета. Физическое удаление может отставать при большой нагрузке.

## Ограничения ресурсов

Workers ограничивают одновременную подготовку. Размер WAV проверяется до и во время загрузки,
формат читается из RIFF chunks, диск не используется. По умолчанию WAV до 128 MB, до 1 млн признаков,
до 200 тыс. совпадений кандидатов на окно поиска. Превышение search limit завершает задачу ошибкой без решения;
неполную выдачу нельзя выдавать за unique. Порог числа признаков проверяется во время их формирования;
пиковую память спектральных кадров дополнительно ограничивает размер аудио. Поиск идёт перекрывающимися окнами по 10 секунд; перекрытие равно MinDuration+MaxGap
(2,8 секунды по умолчанию). При переполнении окно уменьшается до 2*MinDuration+MaxGap.
Это ограничивает память кандидатов независимо от длительности файла. Результат сообщает
один подтверждённый участок, а не суммарную длительность всех повторов.
Для каждого хеша читается не более MAX_HASH_POSTINGS+1 записей; слишком частые хеши исключаются.
Если исключено более половины разных хешей окна, выполняется поиск без фильтра, с тем же
жёстким лимитом. Переполнение после уменьшения окна — ошибка, без фиксации unique.
Для candidate SQL используется некэшируемый план с фактическими параметрами: generic plan
на разных scope и размерах массивов в испытаниях приводил к многоминутным задержкам.

Частые признаки и многократные копии увеличивают индекс и число совпадений. Перед эксплуатацией
нужны измерения потери recall от частотного фильтра на целевом корпусе. Доля совпадений ограничивается
покрытием, но отдельного точного аудиоверификатора пока нет. Длинные шумы/тональные сигналы
могут давать ложные срабатывания. Источник качества — отдельный размеченный корпус речи.

## Сбои и жизненный цикл

- До commit: повтор обработки безопасен, незавершённая транзакция откатывается.
- После commit: повтор входа читает сохранённый результат, S3 и FFT не запускаются повторно.
- После публикации до отметки outbox: событие может дублироваться со стабильным event_id.
- После отметки outbox до Ack: повтор входа только подтверждается после проверки состояния.
- После истечения TASK_RETENTION: прежний task_id снова может обрабатываться как новый;
  окно идемпотентности должно превышать срок хранения/переигрывания входных сообщений.

Shutdown прекращает приём, позволяет задачам завершиться до SHUTDOWN_TIMEOUT, затем отменяет
их контексты и закрывает AMQP connection. Outbox работает до остановки входных обработчиков.
Readiness проверяет PostgreSQL и активный consumer; healthz показывает живой процесс.
При AUTO_MIGRATE=true миграция v1 выполняется при старте под отдельной advisory lock;
при false runtime проверяет версию схемы, а миграцию запускают отдельно через cmd/migrate; дальнейшие изменения схемы
нужно оформлять версионированными миграциями, а не изменением существующего SQL.

Для эксплуатации использовать TLS (amqps, PostgreSQL sslmode verify-full, HTTPS S3/OTLP),
ограниченную IAM роль, отдельные секреты и резервное копирование PostgreSQL.
Локальный collector использует debug exporter; для SigNoz настроить OTLP exporter на его collector.
